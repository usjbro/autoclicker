# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo contains **Autoclicker Void**, a Roblox idle-clicker game: a Luau/Rojo project (`src/`, `default.project.json`) with server-authoritative state and a global leaderboard. `build.rbxlx` is a local build artifact (regenerate it with `rojo build`, don't rely on it as source of truth) and isn't tracked in git. See `GEMINI.md` for the original design brief it was built from.

`my-new-game/` is unrelated, unused Rojo scaffolding (default `rojo init` boilerplate with placeholder "Hello world" scripts) — not part of the real project. `__pycache__/` contains stale compiled artifacts with no corresponding source in the repo; ignore it.

Upgrades (base + Mega Auto-Clicker, Click Power, Global Multiplier) are all priced with **flat, non-scaling costs** — see `src/shared/GameConstants.lua`'s `UPGRADES` table — plus a rebirth/prestige system.

`AutoClicker`/`MegaClicker` `Rate` values are **per-minute**, not per-second (`GameLogic.CalculateIdleGain` divides by 60 internally); the server's idle-gain loop still ticks every `TICK_RATE` (1) second, it just adds a smaller fractional amount each tick.

## Autoclicker Void

### Tech stack
- **Luau** scripting, synced via **Rojo** (`default.project.json` maps `src/` into the Roblox instance tree).
- **TestEZ** for unit tests (`.spec.lua` files under `src/tests/`), vendored under `src/Packages/TestEZ` (see `THIRD_PARTY_NOTICES.md`) and synced by Rojo to `ServerStorage.TestEZ` so it's present on every Studio playtest, not just an optional dependency you have to install yourself.
- **DataStoreService** for persistence.

### Sync workflow
```sh
rojo serve
```
Then connect via the Rojo Studio plugin.

### Architecture — server-authoritative state
The server is the source of truth for scores and purchases; the client only renders state pushed to it and fires input events.

- `src/shared/GameConstants.lua` — shared constants: the `UPGRADES` table (flat `Cost`/`RobuxCost`/`DevProductId` plus `Rate`/`Bonus` per upgrade id), `UPGRADE_FIELDS` (upgrade id → session field name), `ITEMS` (Wings/WingsVoidtech/WingsDragon/WingsDemonic/WingsFae/FlameTrail/LightTrail — one-time-owned, same `Cost`/`RobuxCost`/`DevProductId` shape as `UPGRADES` but granted as a boolean flag, not a stacking count; the 5 Wings styles are an escalating price ladder rather than flat-per-item like the trails, since each independently grants flight — see `FlightSystem.lua` below), `ITEM_FIELDS` (item id → boolean session field name), `MAZE_GOALS` (maze wing goal part name → session field + permanent click/minute reward, see `MapBuilder.lua`/`GameService.server.lua` below), `REBIRTH` (threshold + permanent bonus), `TICK_RATE`, DataStore keys.
- `src/shared/GameLogic.lua` — pure functions for cost lookup (`GetUpgradeCost`), click/idle gain (`CalculateClickGain`, `CalculateIdleGain`), the income multiplier (`CalculateMultiplier`, combines Global Multiplier upgrades and rebirths), rebirth eligibility (`CanRebirth`), and the canonical blank-session shape (`GetDefaultSession`). `ResetProgress`/`PerformRebirth` are the single source of truth for "what survives a reset" — both zero score + upgrade counts and the four `completedMazeNorth`/`South`/`East`/`West` flags (a maze-completion bonus is a repeatable-per-run payoff, not a permanent unlock) but preserve `totalClicks`, `rebirthCount`, speed preferences, **and owned items** (`ownedWings`/`ownedWingsVoidtech`/`ownedWingsDragon`/`ownedWingsDemonic`/`ownedWingsFae`/`ownedFlameTrail`/`ownedLightTrail`/`equippedCosmetic`/`equippedWings` — items are owned until rebirth, not wiped by an ordinary reset); `PerformRebirth` does everything `ResetProgress` does, plus incrementing `rebirthCount` and explicitly clearing all 7 item/equip fields (the one place items *do* get wiped, alongside the maze flags that already reset unconditionally). `CalculateMazeBonusRate(session)` sums `GameConstants.MAZE_GOALS`' `RewardPerMinute` for every completed flag (written as four explicit field checks, not a loop indexing `Session` by a dynamic key, since `Session` is a fixed-field record type under `--!strict`) and feeds into `CalculateIdleGain`'s rate the same way `AutoClicker`/`MegaClicker` counts do, subject to the same multiplier. Required by both server (validation) and client (UI display) so the math can't drift between them.
- `src/shared/NumberFormat.lua` — `Format(n)` abbreviates large numbers (1000 → "1K", 1500000 → "1.5M", etc., continuing past T with two-letter suffixes). Used everywhere a number is displayed, client-side only.
- `src/shared/SpeedCalculator.lua` — the single centralized place movement-speed math lives: `BASE_WALK_SPEED`, `CalculateMaxSpeed(score)` (capped, clamped against invalid input; deliberately based on current score, not `totalClicks`, so buying upgrades lowers it and a Reset/Rebirth brings it back to base -- not a one-way permanent stat), and `CalculateEffectiveSpeed(session)` (base speed if `useBaseSpeed`, otherwise interpolated between base and max by `speedSliderPercent`). Used by both `MovementSystem` (server, authoritative) and the client (display only).
- `src/server/SessionStore.lua` — owns `activeSessions` (per-player state keyed by `UserId`) privately; no other module ever gets the raw table. Every read/write goes through a locked accessor: `With(userId, fn)` (acquire `SessionLock`, look up, call `fn(session)` if it exists -- the workhorse, used by almost every handler), `Install`/`Remove` (for `PlayerAdded`/`PlayerRemoving`, run `fn` inside the same critical section as the table mutation), `Peek(userId)` (unlocked bare read, only for call sites proven safe -- see the file's own comments for the current list and why each is justified), `UserIds()` (snapshot for iteration), and `ForEachSession(fn)` (unlocked bulk read, currently only the leaderboard's periodic save loop). This makes it structurally impossible for a future call site to bypass the lock and reintroduce the session-table races `SessionLock` was built to close.
- `src/server/GameService.server.lua` — handles `ClickEvent`/`PurchaseEvent`/`ResetEvent`/`RebirthEvent`/`UpdateSpeedSettingsEvent`/`PurchaseItemEvent`/`EquipCosmeticEvent`/`ActivateFlightEvent` from clients (all via `SessionStore.With`), runs the idle-gain loop (`task.spawn` loop on `GameConstants.TICK_RATE`, snapshotting `SessionStore.UserIds()` before iterating), and pushes state to clients via the `SyncState` RemoteEvent. Since movement speed is score-based (see `SpeedCalculator`), the shared `syncPlayer` helper itself reapplies `MovementSystem.ApplyEffectiveSpeed` when `useBaseSpeed` is false (skipped otherwise, since base speed is a flat constant regardless of score) right before firing `SyncState` -- centralized there rather than duplicated at every score-mutating call site (`ClickEvent`, `PurchaseEvent`, `ResetEvent`/`RebirthEvent`, the idle-gain loop), since all of them already call `syncPlayer` right after mutating score, so a future score-mutating handler can't forget it. `ResetEvent`/`RebirthEvent` sync first, then save durably via `DataManager.Save` immediately afterward (rather than only relying on the eventual `PlayerRemoving` save, so a reset/rebirth can't be lost to an unclean disconnect) -- sync-before-save specifically so the player sees their reset take effect immediately rather than waiting on a DataStore round-trip that can take seconds under write throttling. `UpdateSpeedSettingsEvent` only ever receives a *preference* (`useBaseSpeed`, `speedSliderPercent`, clamped/validated) — the actual `WalkSpeed` is always recomputed server-side, never taken from the client. `PurchaseItemEvent` grants a one-time `GameConstants.ITEMS` purchase (`session[field] = true`, no-op if already owned/unaffordable — distinct from `PurchaseEvent`'s stacking `+= 1`). `EquipCosmeticEvent` switches `equippedCosmetic` among owned cosmetics via three explicit literal-assignment branches (not a generic loop indexing `Session` by a dynamic field name — `Session` is a fixed-field record type under `--!strict`, so that wouldn't type-check assigning into a narrow union field) and calls `CosmeticsSystem.ApplyEquippedCosmetic` so an already-spawned character updates immediately. `ActivateFlightEvent` takes no arguments and just calls `FlightSystem.TryActivate` — the client only ever asks to fly, the server alone decides whether that's allowed and what it does. Loads/saves sessions via `DataManager` on player join/leave (via `SessionStore.Install`/`.Remove`). Also builds the void environment (`VoidBox`, `VoidFloor`, `VoidSpawn`) and then the explorable map (`MapBuilder.Build()`) before any `Player` connections, so a joining player can never spawn before the floor or map exist; a failure in either is `warn()`-ed and non-fatal to the rest of the gameplay wiring. If the map built, `wireMazeGoal` finds each wing's goal part (named by `MapBuilder`, e.g. `MazeNGoal`) and connects `Touched` — a player's character touching it grants that wing's one-time-per-run click/minute bonus (`completedMazeNorth`/etc.) via `SessionStore.With`, syncs, and saves durably, same reasoning as `ResetEvent`/`RebirthEvent`. Four explicit calls (not a loop indexing `Session` by a dynamic field name from `GameConstants.MAZE_GOALS`) because `Session` is a fixed-field record type under `--!strict`.
- `src/server/MapBuilder.lua` — builds the explorable layout for Movement mode: a multi-level, 3D-chess-style maze spanning the whole map (issue #41), parented under a single `Map` Folder in `workspace`. Exposes `Build(): (boolean, string?)`, pcall-wrapped like the void-environment block that calls it. Pure geometry (all parts `Anchored`, no RemoteEvents/gameplay state of its own — see below) built via small helpers (`createRamp`, `createStaircase`, `createPlatform`, `createPillar`, `createArch`, `createFloatingPlatform`). One maze "wing" extends outward from spawn in each of the four compass directions (`buildMazeWing`, called once per direction from `Build()`) — all four share the same generation/geometry code (`generateMaze`/`buildMazeLevel`/`buildMazeWall`/`buildMazeShaft`), parameterized by which world axis is "outward" for that wing via `mazeLocalToWorld` (and the shared `MAZE_DIRECTION_INFO` table it and everything else reads axis/sign from), so the maze logic exists once rather than once per direction. Each wing has its own difficulty and color theme via `WING_CONFIGS` (North: 5x8 cells, 1 level, green; South: 7x16, 2 levels, yellow; East: 9x20, 3 levels, orange; West: 11x26, 5 levels, red) — grid size and level count both thread through as parameters (not shared module constants) into every maze-geometry function, and each wing's own sub-`Folder` gets a post-build recolor pass (`paintWing`, Neon parts → the theme's trim color, everything else → structural) rather than threading color overrides through the shared geometry helpers, which are also used by non-maze decoration that should keep the default palette. Each level is an independently generated perfect maze (randomized recursive backtracker, `Random.new()` reseeded fresh every `Build()` call so the whole layout varies session to session) stacked directly above the one below and connected by a staircase shaft alternating grid edges each transition, so climbing to the top of a wing means actually crossing each intermediate level rather than riding a single elevator column. Each level's floor and ceiling are each one continuous platform (`buildMazeFloor`, called twice per level -- once at floor height, once with its underside flush against every wall's top) -- connectivity between cells is expressed entirely by `buildMazeWall` (a wall on every non-open edge, reaching the ceiling with no gap), not by gaps in the floor; an earlier version relied on floor gaps alone, which a player could just jump across in a straight line, and a later wall-only version relied on wall height alone, which didn't reliably stop jumping over or camera-tilting to see over a wall from outside. A full floor-wall-ceiling enclosure closes off both by construction rather than by tuning a height number. `buildMazeLevel`'s `openEdges` parameter is the only place a wall is deliberately omitted -- the entry ramp's landing cell (Level 1 only), wherever a shaft's landing bridges back into a level from below, and wherever a shaft departs upward from a level. The top level also gets a named goal marker (`wingName .. "Goal"`, e.g. `MazeNGoal`, plus a purely decorative `GoalBeacon`) at the same lateral column the entry ramp uses — `GameService.server.lua` finds these by name after `Build()` returns and wires the actual completion reward, keeping this file pure geometry. Leaves a clear radius around `VoidSpawn` (origin) so nothing overlaps a spawning player (each wing's gate sits at `MAZE_GATE_DEPTH`, checked -- along with the floor/ceiling-vs-next-level's-floor vertical clearance and each wing's lateral half-extent staying well under `MAZE_ENTRY_DEPTH` (so no two wings' corridors can ever geometrically overlap) -- via `assertMazeConstants()` from inside `Build()`'s own `pcall`, not at module load, which would otherwise crash `GameService.server.lua`'s unprotected `require(MapBuilder)` and take down every RemoteEvent handler in the game, not just the map, if any check ever failed; the spawn ring's own pillars are offset 15 degrees off the cardinal angles so none of them sit on a wing's gate corridor), and uses the client's palette (`#1e1e2f`/`#2a2a3f` structural darks, `#6c5ce7` Neon accent trim) for the spawn-ring/skyline decoration outside any wing's own themed sub-folder.
- `src/server/DataManager.lua` — wraps `DataStoreService` (store name = `GameConstants.STORAGE_KEY`) for per-player load/save; falls back to `GameLogic.GetDefaultSession()` on any failure. `LoadRaw(userId)` is a `Player`-less variant (returns `nil` on failure) used by `LeaderboardManager` for offline players' stats.
- `src/server/MovementSystem.lua` — the only place `Humanoid.WalkSpeed` gets set. `ApplyEffectiveSpeed(player, session)` computes it via `SpeedCalculator` and applies it; `Start` (given the shared `SessionStore`) reapplies it on every `CharacterAdded` via `SessionStore.Peek` (a read-only lookup, not routed through `With` -- it doesn't mutate the session, so locking would only add contention with no correctness benefit). `GameService` also calls `ApplyEffectiveSpeed` directly right after loading a session, in case the character already spawned before the load finished.
- `src/server/CosmeticsSystem.lua` — the only place a cosmetic trail gets attached, mirroring `MovementSystem`'s shape. `ApplyEquippedCosmetic(player, session)` clears any existing trail/particle/fire/light instances on the character's `HumanoidRootPart` by fixed name, then (if `session.equippedCosmetic ~= "None"`) builds three parallel `Trail` ribbons (left/center/right, each its own `Attachment` pair) rather than one — a single flat ribbon reads as a thin line from most viewing angles even at a wide `WidthScale`, so three overlapping ones (each tapered via `WidthScale`, oriented via `FaceCamera`) is what actually reads as a wide, voluminous streak — plus a single "tail" `Attachment` carrying a `ParticleEmitter` (both variants now, sized as a growing `NumberSequence` to mimic real fire/smoke expansion), a `PointLight` (real illumination on nearby surfaces, not just an emissive-looking material), and (flame variant only) a stock `Instance.new("Fire")`. Every effect here uses stock Roblox defaults only — no custom Texture/Image assets, same constraint the client's Unicode nav-button glyphs already work around. `Start` reapplies it on every `CharacterAdded` (a fresh spawn has none of the old instances); `GameService`'s `PurchaseItemEvent`/`EquipCosmeticEvent` handlers also call it directly (already inside `SessionStore.With`) so an already-spawned character updates without needing to respawn.
- `src/server/FlightSystem.lua` — `TryActivate(player, session)` is the only way a flight burst happens. Checks `session.ownedWings` and a per-`userId` cooldown (module-private, in-memory, not session data — same reasoning as `LeaderboardManager`'s username/click caches), then applies a `LinearVelocity` constraint (forward look-direction + a fixed upward bias) for a few seconds before removing it. The client's `ActivateFlightEvent` carries no arguments and reports no duration/velocity/position -- every parameter of the effect is decided here, server-side.
- `src/server/LeaderboardManager.lua` — wraps a separate `OrderedDataStore` (`GameConstants.LEADERBOARD_KEY`) for the top-10 global leaderboard, sorted by score. Entries also include `totalClicks`, pulled from the live session (via `SessionStore.Peek`) if that player's online or via `DataManager.LoadRaw` otherwise. Refreshes every 60s, broadcasts via the `LeaderboardUpdate` RemoteEvent, caches usernames to avoid API throttling, and degrades gracefully (warns + serves cached data) if DataStore API access isn't available (e.g. in Studio without API access enabled). `SaveScore(player, score, force?)` skips writes `<= 0` by default (avoids a spurious "0 score" entry for a never-played player) unless `force` is passed, which `ResetEvent`/`RebirthEvent` use to immediately reflect a wipe for a player who already has an entry. Writes are serialized per player (a `saveInFlight`/`pendingSave` pair keyed by `userId`) rather than each call firing its own independent `task.spawn`'d `SetAsync` -- at most one write per player is ever in flight, and a call that arrives mid-write just updates `pendingSave` for the in-flight loop to pick up next, so completions can't land out of order and silently let a stale score overwrite a newer one.
- `src/server/RobuxPurchaseManager.lua` — handles the Robux alternate-currency path via `MarketplaceService.ProcessReceipt`, granting the matching upgrade or item on the player's active session (via `SessionStore.With`, which replaces its own former direct `SessionLock.Run` call). A single `productIdToGrant` reverse lookup covers both `GameConstants.UPGRADES` and `ITEMS` (tagged `{kind: "Upgrade" | "Item", id}`), since the grant/rollback logic differs: an upgrade stacks (`+= 1`, rolled back with `-= 1` on a failed save), an item is one-time-owned (`= true`, rolled back by restoring whatever the flag was before, not hardcoding `false`). Tracks processed receipt ids in their own DataStore (`GameConstants.RECEIPT_STORE_KEY`) so a real-money purchase is never silently lost or double-granted across retries/restarts. **`DevProductId`s in `GameConstants.UPGRADES`/`ITEMS` are placeholder `0`s** — create matching Developer Products in the Roblox Creator Dashboard (Monetization > Developer Products), one per upgrade/item, priced at its `RobuxCost`, then paste the resulting numeric ids in; the client's Robux buy buttons stay disabled ("Coming soon") until then.
- `src/client/init.client.lua` — builds the entire UI programmatically (no `.rbxlx`-authored UI) with a dark theme (`#1e1e2f` background, `#6c5ce7` accent), driven by a single `currentScreen` state (`"Clicker" | "Shop" | "Settings" | "Movement"`) via `setScreen()` so only one screen is ever visible at once. Bottom-right: 3 stacked dark-gray icon buttons (Clicker/Shop/Settings — Unicode glyphs, since uploading custom Roblox image assets isn't available here) plus a separate blue "Toggle Moving" button. Clicker screen is a persistent-feeling top HUD (score/rate/total clicks/rebirths/click button); Shop and Settings are centered popups; Movement mode hides the nav stack and whichever panel was open, showing a minimal top stats bar and a left-side return button instead, leaving the map unobstructed. Settings has a custom drag-slider (Roblox has no built-in one) for movement speed, echoing the server's authoritative value rather than trusting local drag state -- deferred while actively dragging or while a just-sent value hasn't round-tripped back yet (bounded by a short timeout, so an out-of-order server apply can't stall the display indefinitely). A top-right panel renders the live leaderboard from `LeaderboardUpdate`. Shop also has an Items section (Wings, Flame Trail, Light Trail — `ITEM_DISPLAY`) below the stacking upgrades: a "Buy"/"Owned" points button, a Robux button (same disabled-until-a-real-`DevProductId` pattern as upgrades), and, for the two cosmetics, an Equip toggle (`EquipCosmeticEvent`, tracked client-side via `lastKnownEquipped`, updated every `SyncState` tick). `Space` does double duty: click (Clicker screen, on the ground) or a flight burst (`ActivateFlightEvent`, owns Wings, `Humanoid:GetState()` reports `Freefall`/`Jumping`) — airborne takes priority over clicking regardless of which screen is open, since flight is tied to the character, not the UI panel.
  - **Responsive sizing**: every panel (Clicker HUD, popup windows, Movement top bar, leaderboard panel) is scale-based (`UDim2` scale component) with a `UISizeConstraint` (via the `addSizeConstraint` helper) clamping it to a sane min/max pixel range, rather than a flat pixel `Size` — this is what the bottom-right nav stack already did and is now the pattern the rest of the GUI follows too. `makeLabel` sets `TextWrapped` + `AutomaticSize.Y` on every label so wrapped text grows a row's height instead of clipping/overlapping its neighbor. Popup windows (`createPopupWindow`, shared by Shop/Settings) size both axes by scale (clamped ~380-460px wide, ~280-620px tall) instead of `AutomaticSize.Y` off a flat pixel width, since Shop's five cards can be taller than a phone viewport; their body is a `ScrollingFrame` (`AutomaticCanvasSize = Y`) below a fixed-height title bar, so overflow scrolls instead of pushing the window off-screen. The leaderboard panel is only shown on the Clicker screen (never behind a popup, which can be wide enough on a small screen to reach its corner) and only when `screenGui.AbsoluteSize` clears a min width/height (re-checked on resize, not just on screen switches) — below that it hides rather than colliding with the Clicker HUD or nav stack. The nav stack sets an explicit `ZIndex` and the `ScreenGui` uses `ZIndexBehavior.Global` so it always renders (and stays clickable) above a popup, in the rare case one still physically reaches its corner on a small screen.

RemoteEvents (`ClickEvent`, `PurchaseEvent`, `ResetEvent`, `RebirthEvent`, `UpdateSpeedSettingsEvent`, `PurchaseItemEvent`, `EquipCosmeticEvent`, `ActivateFlightEvent`, `SyncState`, `LeaderboardUpdate`) are declared in `default.project.json` under `ReplicatedStorage`, not in a `.lua` file. Robux purchases go through Roblox's built-in `MarketplaceService` APIs instead, not a custom RemoteEvent.

Characters spawn normally (`Players.CharacterAutoLoads` is left at its default) and walk around a flat black floor inside a large black `VoidBox`, with Roblox's default third-person camera/movement (from `PlayerModule`/`CameraModule` under `StarterPlayerScripts`) — no custom camera code. `MovementSystem` overrides `WalkSpeed` only; movement itself is entirely stock Roblox. Health/Backpack CoreGui stay hidden client-side since this game has no combat/damage. The client's "Movement mode" toggle is a pure UI state (which panels are visible) — the character can always physically move regardless of which screen is showing.

Three project-scoped skills encode the patterns above: `.claude/skills/roblox-feature-scaffold` (the RemoteEvent → `SessionStore.With` → validate → `syncPlayer` → durable-save-if-needed shape for adding a feature), `.claude/skills/roblox-security-review` (checks every RemoteEvent handler's client-input validation against the exploit surface described in "Architecture — server-authoritative state"), and `.claude/skills/roblox-responsive-ui` (the scale-based `UDim2`/`UISizeConstraint` pattern for `src/client/init.client.lua`, plus a checklist of gotchas — `UIScale` vs. tweening a clamped `Size`, overlap thresholds derived from real clamped widths rather than magic numbers — that have each already caused a real bug here). All three cite specific functions/files in this section — if the session-mutation pattern, `SessionStore`, a new manager module, or the client's responsive-sizing approach changes, check whether the relevant `SKILL.md` needs updating too, the same way the Lune/TestEZ suites below need to stay in sync with each other.

### Tests
Unit tests live in `src/tests/*.spec.lua` (`GameLogic.spec.lua`, `NumberFormat.spec.lua`, `SpeedCalculator.spec.lua`) and run automatically on server startup via `src/tests/runner.server.lua`, which bootstraps TestEZ (vendored under `src/Packages/TestEZ`, synced to `ServerStorage.TestEZ` — see "Tech stack" above; the `FindFirstChild` lookup falls back to a warn-and-skip if a stale Rojo sync hasn't picked it up yet, rather than erroring) and auto-discovers every `.spec.lua` file under `src/tests/`. These only execute inside a running Roblox server session (Studio or a live server) — there's no CLI runner for them.

For the pure logic in `src/shared/` (`GameLogic.lua`, `NumberFormat.lua`, `SpeedCalculator.lua`) specifically, `test/gameLogic.test.luau` runs the equivalent assertions headlessly via [Lune](https://lune-org.github.io/docs) (`brew install lune`, then `lune run test/gameLogic.test.luau`) — no Studio needed. This works because `GameLogic.lua`'s one `require` call branches on whether the Roblox-only `script` global exists, falling back to a Lune-style relative require otherwise (`NumberFormat.lua`/`SpeedCalculator.lua` have no internal requires, so they need no such branch); the files are otherwise unmodified between the two runtimes. `test/` lives outside `src/` on purpose so Rojo never syncs it into the Roblox place. Keep the Lune and TestEZ suites' test cases in sync when either changes.

## Development workflow

`main` is the single trunk branch — it's what's kept local and deployed to Roblox, and it should always be in a known-good, tested state. There is no separate long-lived integration branch; every other branch merges directly into `main`. Work happens on short-lived branches, one per issue or fix, merged back via PR:

1. Branch off the latest `main`: `git checkout -b fix/<short-description>` (or `feature/`, `chore/` for non-bug work).
2. Make the change. Run these locally before pushing:
   ```sh
   lune run test/gameLogic.test.luau
   rojo build default.project.json -o /tmp/check.rbxlx
   rojo sourcemap default.project.json -o sourcemap.json
   luau-lsp analyze --platform roblox --sourcemap sourcemap.json --definitions globalTypes.d.luau src/server src/shared src/client
   ```
   The first two don't execute or type-check any server/client Luau — `lune` only runs the specific pure-logic files it requires, `rojo build` only compiles the place-file structure — so `luau-lsp analyze` is what actually catches an invalid `Enum` reference or an argument-type mismatch before it ever reaches Studio (see issue #43/PR #44, which shipped a crash-on-load bug neither of the first two checks could have caught). It's scoped to `src/server`/`src/shared`/`src/client` only — `src/tests/*.spec.lua` and the vendored `src/Packages/TestEZ` are excluded, since TestEZ ships no Luau type definitions for `luau-lsp` and the enforced test surface is the Lune suite above, not the in-Studio TestEZ one.
3. Open a PR against `main` (`.github/PULL_REQUEST_TEMPLATE.md` has the checklist). GitHub Actions (`.github/workflows/ci.yml`) runs the same three checks automatically on every PR, regardless of target branch, plus every push to `main`, using `lune`/`rojo`/`luau-lsp` versions pinned in that file — a local `brew install lune`/`brew install rojo`/`brew install luau-lsp` tracks whatever's current in Homebrew instead, so if an upgrade ever changes behavior, CI and a local run can disagree until `ci.yml`'s pinned versions are bumped to match.
4. `main` has branch protection requiring a PR (not a direct push) and a passing CI run before merging. Repo settings only allow squash-merging and auto-delete the branch afterward, enforcing that step too rather than relying on remembering to do it manually.
5. Prefer reviewing the diff (manually or via the `/code-review` skill) before merging, especially for anything touching `src/server/` — this codebase has already hit real concurrency bugs (shared per-player session state mutated from multiple RemoteEvent handlers/DataStore callbacks) that surfaced only under review, not from casual reading.

**The `dev` branch is not part of this project.** It diverged at the very first commit and contains an unrelated Python OCR-based screen-automation tool (`main.py`, `logger.py`, `ocr_detector.py`) that happens to share this repo by name collision. Don't merge it into or base work off of it.
